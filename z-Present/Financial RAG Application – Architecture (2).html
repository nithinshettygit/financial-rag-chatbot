Financial RAG Application

A question-answering service over financial filings. It checks the question, finds the right filing passages, writes an answer from them and returns the answer with its sources.

1Groq model for planning, policy checks and answers
384Embedding dimensions (BGE-small)
30 → 5Candidates per retriever, then final chunks
4,096Max evidence tokens per answer
80 sServer deadline per chat request
24 hAnswer cache lifetime

Who it is for

People who ask questions about companies in the indexed filings, such as a metric for a given year or a comparison of two companies. Operators use a separate admin tool to load documents.

What it does

  • Accepts a chat message and decides whether it is in scope.
  • Resolves follow-ups into a company, year and metric.
  • Searches with dense vectors and BM25 in parallel, then reranks.
  • Answers only from the retrieved evidence, with [S1]-style source tags.
  • Checks the answer and returns it with the supporting chunks.

End-to-end architecture, one picture

The whole system in four zones: ingestion, shared stores, the online chat path and offline evaluation. Scroll sideways on small screens.

How to read it

  • Zone 1. An operator uploads a PDF or a manifest. Docling parses it into chunks, which are validated, embedded and written to Qdrant. The manifest also feeds BM25.
  • Zone 2. Qdrant, the manifests, the catalog and Redis are shared. Ingestion writes them. The online path reads them.
  • Zone 3. A chat request is limited, checked, planned, cache-checked, searched, reranked, answered and verified. The path runs down the left column, then up the right.
  • Zone 4. The evaluation runner calls the same live pipeline, stores the samples and scores them with RAGAS.

Response contents

  • Answer text, normalised intent and the standalone search query.
  • Updated session state: company, fiscal year, target metric, document ID.
  • Retrieved chunks with ID, text, document, file, page, type, headings, fusion score and reranker score.
  • A source map from tags to file, page and section.

Startup and shutdown

  1. Observability is set up for FastAPI and outbound HTTP.
  2. Warmups run concurrently: Qdrant embeddings, BM25 load, reranker client, cache index, guardrails, PII engine, intent examples, Groq clients.
  3. A forced catalog refresh runs.
  4. Only then is the service marked ready. A required warmup failure stops startup. Cache and intent warmup failures degrade quietly.

Data

The corpus is financial filings, parsed into chunks. Chunks live in two places that must stay in step.

Document catalog

  • Built from Qdrant payloads, grouped by document and source file.
  • Refreshed every 300 seconds, and once at startup.
  • Falls back to BM25 chunks if Qdrant returns no rows.
  • A corpus fingerprint from document IDs and chunk counts scopes the cache.

Ingestion pipeline

A separate Streamlit admin tool handles ingestion. It is protected by two logins.

  1. Parse PDFs with Docling, or accept existing manifests.
  2. Write chunk manifests to the shared manifest folder.
  3. Seed the configured Qdrant collection with named-vector embeddings.

Chunk metadata used at search time

  • Document ID, file name, company and fiscal years.
  • Page, section headings and chunk type.
  • Financial metric, table columns and row labels, which help BM25 and reranking match table content.
The admin tool and the API must point at the same Qdrant collection and vector name, and see the same manifest folder.

Answer generation

Prompt and context

  • Model: Groq openai/gpt-oss-20b, temperature 0.
  • The prompt requires evidence-only answers, exact values and units, citations, and a clear note when data is missing.
  • Evidence is packed in rank order up to 4,096 tokens. Each source gets a tag such as [S1] and a source map.

Hallucination controls

CheckRule
Prompt leakBlocks answers that expose internal instructions.
Output PIIMasks sensitive entities and secrets.
Numeric groundingCompares figures with the evidence. Allows ×1,000 and ×1,000,000 scaling with 1% tolerance. Blocks if more than half cannot be matched.
Strict retryA numeric block on the first try triggers one retry with a stricter prompt. Other blocks do not retry.
CompletenessEvery requested company must appear in the evidence. Otherwise a note is added and the answer is not cached.

Cache

  • L1 exact: Redis key from scope and normalised query.
  • L2 semantic: RedisVL, nearest match only. Cosine distance at most 0.04, term overlap at least 0.7, and matching numbers.
  • Scope: intent, companies, years, document IDs and corpus version.
  • Only complete, passing answers are stored, in the background.

LLM retries

Up to 4 attempts, with at most 25 seconds of total waiting. Rate limits rotate to a second key if one is set.

What each step does

  1. Access. Nginx asks for Basic Auth from a mounted password file. The app then asks for its own username and password. XSRF protection is on. WebSocket upgrade headers are forwarded and buffering is off.
  2. Input. The operator uploads PDFs, or points to manifests that already exist. Uploads sit in a named volume.
  3. Parse. Docling parses the PDF and chunks it. Tables and headings are kept as metadata such as columns and row labels.
  4. Manifest. Chunks are written as JSON arrays into the shared manifest folder. The API and admin containers both mount it.
  5. Seed. Chunks are embedded and loaded into the configured Qdrant collection with the configured named vector. The remote Qdrant URL and key are required.
  6. Pick-up. The API sees new documents in its catalog within 5 minutes. BM25 does not reload until the API restarts.

BM25 manifest loading

  • Reads JSON files from the manifest folder first. If none, scans the data folder, except the metadata subfolder.
  • Skips files that start with old_, contain _old or cache or evaluation, or end in .bak.
  • Accepts only JSON arrays. Drops empty chunks and sentinel values.
  • Indexes searchable text built from document, file, company, years, metric, headings, columns, row labels, embedding text and content.

Admin edge limits

  • 5 requests per second per client, burst 10, no delay. Static admin assets are excluded.
  • 20 connections per client. Read timeout 300 s.
  • Admin container: 3 GiB memory.

Conversion

  • PDF only. Device is auto, CPU, CUDA or MPS. Four threads.
  • OCR mode auto first converts without OCR. If more than 20% of pages have no content, it converts again with OCR. If OCR fails, the first result is kept.
  • Modes on and off force the choice.

Token budget

  • Embedding text is capped at 500 tokens, under the 512 limit of BGE-small.
  • Room is reserved for the Document / Page / Section prefix added to every chunk.
  • Text is never cut. Oversized text is split in order: lines, then sentences, then words, then raw token slices.
  • Text chunking uses Docling's hybrid chunker with peer merging off.

Noise filters

Chunks with fewer than 35 characters or 6 words are dropped. Phone numbers, employer ID lines, executive-office lines and checkbox glyphs are treated as boilerplate. Adjacent short text fragments are merged.

Steps

  1. Validate. The manifest must be a JSON array of objects. Text fields must be strings, document and chunk IDs must not be empty, and metadata must be an object.
  2. Connect. Remote Qdrant when a URL is set, otherwise local storage.
  3. Collection. Created if missing, with the named vector at 384 dimensions and cosine distance.
  4. Indexes. Keyword indexes on document ID, chunk type and company. Integer indexes on fiscal year and fiscal years.
  5. Embed. FastEmbed BGE-small on the embedding text, falling back to content. Batch size 32.
  6. Points. The point ID is a UUID5 of document ID and chunk ID. Re-indexing the same document therefore overwrites, not duplicates.
  7. Upsert. All points are sent in one call.
  8. Clean up. For each document, points that are not in the new set are deleted. This removes stale chunks after a re-parse.

Payload stored with each vector

Chunk ID, document ID, source file, content, embedding text, page, fiscal year and years, headings, chunk type, columns, row labels, financial metric, table caption, row group, company and the full metadata object.

Inference fallbacks

  • Company: taken from the chunk, then from metadata, then inferred from the document ID for known names.
  • Fiscal year: taken from the chunk or metadata, then inferred from a 20xx year in the document ID or file name.

Evaluation

Answers are scored with RAGAS on a fixed question set. The run calls the real pipeline, so retrieval, guardrails and generation are all in the loop.

0.913Context precision
1.000Context recall
0.870Faithfulness
0.973Answer relevancy
25Questions scored, 0 problems

Method

  1. Load the question set. Each item has a question and a reference answer.
  2. Run each question through the live pipeline, two at a time.
  3. Keep up to 5 retrieved contexts, each cut to 1,500 characters. Cache these samples so scoring can be repeated.
  4. Score four metrics with a Groq-hosted judge. Calls fail over across keys and across two judge models, and back off on rate limits.
  5. Answer relevancy uses BGE-small embeddings. Results go to a per-question CSV and a summary.

Pass the refresh option to re-run the pipeline instead of using cached samples.

Query planner and session state

Inputs

  • The masked, safe query.
  • Up to the last 4 turns, within a 6-turn bound. History is capped at 12 messages of 2,000 characters. Assistant turns are cut to 600 characters for the router.
  • Current state, known company names, and the embedding-router hint.

Router output (Groq JSON mode)

Rule-based clean-up after the model

  • Company names are lowercased, tokenised and stripped of suffixes such as Inc, Corp, Ltd and Company, then matched to the catalog.
  • A separate detector finds indexed companies named in the query.
  • Years: the pattern accepts 2010–2039. Model years are accepted from 1990–2100. With no year, the state year may be used.
  • With no model metrics, verbs, years and company names are stripped to get a metric phrase. A follow-up may reuse the earlier metric.
  • Subqueries are capped at 12. Default elaboration aspects: segment, product or region breakdown, drivers and management commentary, and year-over-year change.

Follow-up detection

There is no follow-up without history. A confident embedding hint and the model verdict are reconciled. Regex fallbacks apply only when the embedding router is off.

Guardrails and PII in depth

Input rails, in order

  1. Mask PII and secrets. API-key patterns are always masked. Presidio with spaCy en_core_web_sm runs at score 0.4. Replacement goes right to left to keep offsets.
  2. Heuristics. Reject empty text, text over 2,000 characters, and known injection phrases such as instruction override and system-prompt disclosure.
  3. Policy check. A Groq self-check allows filing questions, follow-ups, greetings, capability questions and chat summaries. It blocks other work and investment advice.

Output rails, in order

  1. Prompt leak. Blocks configured markers of internal instructions.
  2. PII mask. Same entities, without phone numbers.
  3. Numeric grounding. Pulls material numbers from the answer. Ignores citation tags and years 1900–2100. Matches against numbers in the evidence with ×1,000 and ×1,000,000 scaling and 1% tolerance. Blocks if more than half fail.

The output rails are deterministic. They make no extra model call.

How the chat limiter works

  • One atomic Redis Lua script with fixed windows aligned to the clock.
  • Both the session and IP counters must be under their limits. Rejected attempts add nothing.
  • IPv6 is grouped by /64. Keys hold a SHA-256 digest of the session or IP.
  • Nginx sets the real client address and overwrites forwarding headers.
  • Headers returned: session limit and remaining, IP limit and remaining, and reset time.
  • Redis failure fails closed with 503.

How the queue works

  • A Redis FIFO. A request leases an active slot for 60 s and renews it while work runs.
  • If the deadline fires, the client gets 504 but the lease stays until the work finishes. This stops hidden overload.
  • A separate in-process semaphore caps active search targets at 8.

Groq client limits

These are client-side retries. The provider quota is set by the Groq account, not by this project. Router calls time out at 20 s and answer calls at 30 s. Retries cover rate limits, connection errors and server errors, with up to 4 attempts and 25 s of total waiting. The wait follows the provider's retry hint when given, otherwise a bounded exponential delay with jitter.

Access and abuse control

  • Signed, random, HttpOnly session cookie. Secure by default. It identifies a session and grants no privileges.
  • Redis rate limits per session and per client IP. IPv6 grouped by /64. Keys use SHA-256 digests, not raw values.
  • Over-limit requests get HTTP 429 with Retry-After. Redis failure fails closed with HTTP 503.
  • The admin tool needs both proxy Basic Auth and its own login. XSRF protection is on.
  • Request bodies are capped at 64 KiB, and 32 MiB for admin uploads.

Input and output protection

DirectionOrder of checks
InputPII and secret masking, then length and injection rules, then an LLM policy check.
OutputPrompt-leak check, PII masking, numeric grounding.
  • Input masking covers phone, email, payment card, SSN, IBAN, IP address, bank number, passport, driver licence, Aadhaar and PAN.
  • Output masking leaves phone numbers alone, so investor-relations numbers survive. Secrets are masked both ways.
  • If Presidio fails, regex masking takes over.
  • Prior chat turns are masked before routing or generation.
  • If rails fail, the request is blocked by default.

Audit and telemetry

  • Logfire spans cover startup, routing, guardrails, search, reranking and LLM calls, with token usage.
  • Spans store a query hash and length, not the raw query.
  • Trace access and retention still need to be set per deployment.

Edge hardening

HTTPS only with TLS 1.2 and 1.3, one-year HSTS, nosniff, same-origin framing and a strict referrer policy.

Operations

  • Qdrant is not in the Compose file. An external URL and key are required.
  • The API health check calls the readiness route, with a 20-minute warmup window.
  • Startup warms Qdrant, BM25, the reranker client, cache, guardrails, PII and intent models, then refreshes the catalog.
  • Nginx gives the API route 145 seconds to respond. The app deadline is 80 seconds.
  • Scaling is bounded by design. One RAG request runs at a time across API processes, and up to 10 wait.
  • Each API worker holds its own in-memory indexes and model objects.
