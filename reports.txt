## Behavior you'll see

| Scenario | Before | After |
|---|---|---|
| "Nike 2026 revenue", then "tell me more about it" | Identical cached answer | A new answer with different details (segments, drivers, year-over-year change), written to avoid repeating the first one |
| "revenue details of Nike", then "revenue sources of Nike" | Same cached answer | Two separate answers, because the word-overlap check rejects the near match |
| "Nike 2026 revenue", then "what about 2025?" | Could reuse the 2026 answer | Rewritten as "Nike revenue 2025" and answered fresh or from the matching cache entry |
| "hi" repeated | Often missed, especially after other questions | First call uses the LLM, every repeat comes from the cache with no LLM call at all |
| Repeat the same elaboration after the same previous answer | Same answer | Same answer from the cache, which is correct, because it's keyed on that previous answer |

## Performance and cost

- **Latency:** every non-greeting question now waits for NeMo's LLM policy check (`self check input`) before the router runs. Expect roughly +0.2–0.5 s per request on a small Groq model. Output rails are deterministic, so they add almost nothing.
- **LLM calls:** one extra call per non-greeting query. The exception is the rare numeric-grounding retry, which adds one more generation.
- **Cache hits:** these still pay for the input check and the router call, because the cache scope depends on the router's entity and year output. They skip retrieval, reranking and generation, so they're still much faster than a miss.
- **Elaboration:** these questions retrieve 3 extra chunks and send the last few turns to the model, so they use more tokens than a normal question.
- **Hit rate:** it will go down. The semantic match is stricter, so paraphrases like "revenue breakdown" and "revenue details" now miss more often. That is the cost of fixing the wrong-answer hits. You can loosen `CACHE_MAX_DISTANCE` and `CACHE_MIN_TERM_OVERLAP` after watching the logs.

## New ways it can go wrong

- **Numeric-grounding blocks:** an answer is blocked when more than half its material figures can't be found in the retrieved text. A calculated growth rate is usually fine, but an answer made mostly of derived numbers can be refused. The pipeline retries once with a stricter prompt before giving up.
- **Over-blocking on input:** the injection regex and the LLM policy check can reject odd but legitimate phrasing. If that happens, check the `blocked_by` attribute in Logfire and adjust `rails.co` or `prompts.yml`.
- **Follow-up misclassification:** a standalone question can occasionally be treated as a follow-up, or the reverse. The regex overrides catch the common cases but not all of them.
- **NeMo failure:** if NeMo errors or times out, the deterministic rules run instead and the LLM policy check is skipped. `degraded` is logged on the Input Guardrails span.

## What to watch first

- `cache_hit` and `cache_tier` on the root span in Logfire.
- The `Cache L2 near-miss` and `rejected by lexical guard` log lines.
- `blocked_by` and `followup_type` in your first day of real traffic.

I haven't run this against live Redis, NeMo or Groq, so treat the first few days as tuning time.
